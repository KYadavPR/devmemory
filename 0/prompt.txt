# Build the MVP: State-Aware AI Coding Loop

You are building a local-first MVP for a developer-experience system that creates a closed feedback loop around an AI coding agent.

The goal is NOT to build a full autonomous software-engineering platform yet.

The goal is to prove this end-to-end loop:

HUMAN TASK
→ ANTIGRAVITY AGENT
→ repository changes
→ tests
→ Git commit
→ Entire checkpoint/context
→ state collection
→ state normalization
→ MCP
→ ANTIGRAVITY reads the new state
→ agent decides what to do next
→ continues working
→ repeat until READY or BLOCKED

The most important requirement is that this loop must actually work on a real local repository.

---

# 1. Core architecture

Implement exactly these logical components:

1. Antigravity

   * The AI coding agent.
   * It must remain responsible for understanding the repository, deciding implementation, editing files, running commands, running tests, and deciding what to do next.

2. MCP Server

   * The interface between Antigravity and our state system.
   * It must expose a small number of tools that return structured project state and checkpoint information.

3. State Engine

   * Aggregates evidence from Git, Entire, tests, and optionally Entire Graph.
   * Produces one normalized machine-readable project state.
   * It must NOT modify application code.

4. Git Collector

   * Reads the current repository state.

5. Entire Collector

   * Reads the latest relevant Entire session/checkpoint information.

6. Test Collector

   * Runs the project's configured test command and captures pass/fail results.

7. Entire Graph Collector

   * Use only a small useful impact query for MVP.
   * Do not build a graph visualization.
   * If Graph integration is unavailable or unreliable in the current environment, make the collector optional and fail gracefully.

8. SQLite

   * Store normalized state/history locally.
   * No PostgreSQL, Redis, Kafka, cloud database, or distributed infrastructure.

9. Minimal dashboard/CLI

   * Show current state for debugging/demo purposes.
   * Keep the UI simple.

---

# 2. Important architectural principle

Do NOT put the entire repository into the state.

The state tells Antigravity:

* what task is being worked on
* what has been completed
* what remains unresolved
* current Git commit
* current Entire checkpoint
* test evidence
* useful change-impact information
* recommended focus

Antigravity must still inspect the actual repository using its normal coding tools.

The model workflow must therefore be:

MCP state
→ understand current situation
→ inspect repository
→ reason
→ modify code
→ test
→ commit
→ refresh state
→ get new state
→ continue or stop

Do NOT make the State Engine decide how code should be implemented.

# 4. State statuses

Support exactly these main states:

IN_PROGRESS
NEEDS_WORK
READY
BLOCKED

Suggested semantics:

IN_PROGRESS:

* task is actively being worked on
* no final completion evaluation yet

NEEDS_WORK:

* one or more requirements are incomplete
* OR tests fail
* OR unresolved issues exist

READY:

* requirements appear complete
* relevant tests pass
* no blocking unresolved items remain
* working tree is clean or otherwise explicitly accepted

BLOCKED:

* agent cannot safely continue
* required external/human decision is needed
* infrastructure/problem prevents meaningful progress

Do not pretend READY means mathematical certainty.
This is an evidence-based state.

The requirement evaluator must use evidence from:

Do not determine requirement completion from Git statistics alone.

For MVP, use an LLM-based requirement evaluation layer only where needed.
Keep the output structured and auditable.

# 13. Agent operating protocol

Create a repository-level AGENTS.md or equivalent Antigravity rule/workflow so the agent follows this loop.

Agent protocol:

1. Before starting or resuming meaningful work, call get_state().
2. Read the returned state.
3. Inspect the actual repository based on the state.
4. Decide the implementation yourself.
5. Make code changes.
6. Run relevant tests.
7. Fix failures.
8. Before declaring completion, commit the source changes.
9. Refresh project state.
10. Get the updated state.
11. If state == NEEDS_WORK, continue.
12. If state == BLOCKED, explain the blocker to the human.
13. If state == READY, stop implementation and report completion.

Important:

The MCP state is NOT a code patch.

Do not blindly obey "recommended_focus" if repository inspection shows it is incorrect.
Treat it as evidence and guidance.

The agent retains responsibility for implementation decisions.

# 14. Closed-loop behavior

This is the most important feature.

Implement this logical loop:

while task_not_terminal:

```
state = get_state()

if state == READY:
    stop

if state == BLOCKED:
    ask_human

inspect_repository()

implement_changes()

run_tests()

commit_changes()

refresh_state()

state = get_state()

if state == NEEDS_WORK:
    continue

if state == READY:
    stop
```

Do not implement this as an infinite background autonomous process.

For MVP, the loop must be controlled by the Antigravity agent conversation and MCP tool calls.
